# 声纹（说话人身份）方案评估设计

- 日期：2026-09-25
- 状态：**待评审，未实现**（本文只做评估与设计，不含任何代码改动）
- 关联：`2026-09-21-local-face-pose-vision-design.md`（已批准）、`apps/voice-service`、`apps/vision-service`、`apps/perception-console`

## 一、要解决的问题

用户问「你知道我是谁吗」，当前助手只能诚实回答「我无法通过声音辨认说话人，我看到画面里有爸爸在卧室，是你吗？」。

这不是缺陷，是已批准设计的直接后果：

1. 视觉侧只产出「谁在哪个房间」（`query_person_location` / `scene_context`），画面里的人和正在说话的人**不是同一个命题**。
2. 已批准设计**明确禁止**用画面推断说话人。理由是误判代价不对称：把妈妈当成爸爸，然后以爸爸的身份执行操作，比答不上来更糟。
3. 语助侧没有第二路证据，因此只能如实说明。

所以「我是谁」目前是**已知的能力空洞**，不是待修的 bug。本文评估是否、以及如何补上这一路证据。

## 二、目标与非目标

**目标**

- 让助手在**有把握**时知道说话人是谁，从而用对人称、说对话（"你" 而不是 "爸爸"）。
- 在**没把握**时保持现在的诚实行为，不退化。
- 身份结论必须**可标来源、可解释、可撤销**，并与人脸的权威链并存而不互相覆盖。

**非目标**

- 不用声纹替代人脸去判断"人在哪个房间"。位置仍然只来自摄像头（`view.room_id = track.camera_room_id`）。
- 不让声纹结论直接触发写操作（开关灯/空调/场景）。见第六节的动作分级。
- 不做"情绪识别""年龄性别推断"这类衍生画像。

## 三、候选方案对比

| 方案 | 做法 | 准确度 | 成本 | 隐私 | 与现有设计冲突 |
| --- | --- | --- | --- | --- | --- |
| A 声纹识别 | 本地 speaker embedding + 已注册声纹库比对 | 中高（取决于语句长度） | 需新增模型与注册流程 | 需本地加密存储生物特征 | 无直接冲突，需新增权威源 |
| B 自报姓名 | 用户说"我是爸爸"，靠对话记忆 | 低（可冒充、可忘记） | 近乎零 | 无 | 无，但不可作为身份依据 |
| C 画面弱推断 | 画面只有一人 → 认定是说话人 | 低 | 零 | 无 | **直接冲突**，已明确排除 |
| D 声纹+人脸融合 | 两路证据取交 | 高 | 高（两路都要维护） | 两者叠加 | 需定义冲突裁决规则 |
| E 永远回问确认 | 不识别，每次追问 | — | 零 | 无 | 无 |

**建议**：采 A（本地声纹）作为**唯一**说话人证据来源，保留 E 作为兜底；B 只作提示不当依据；C 维持排除；D 暂不做（本轮没有第二路可靠证据时融合无收益）。

## 四、评估维度与建议门槛

声纹在**短语音**上不可靠，这是本方案最大的工程约束：唤醒词之后的"开灯"只有约 0.6–1.0 秒，远场混响下更差。因此门槛必须绑定语句长度。

| 维度 | 建议门槛 | 说明 |
| --- | --- | --- |
| 等错误率 EER | ≤ 5%（1.5 秒以上语音） | 低于 1.5 秒不下结论，直接走兜底 |
| 误接受率 FAR | ≤ 1% | 误接受比误拒绝危险得多 |
| 结论延迟 | ≤ 300 ms | 必须落在现有 `agent_deadline`（20 秒）预算的零头里 |
| 运行成本 | CPU 可跑 | 现有 GPU 已被 InsightFace + YOLO 占用，不能再抢显存 |
| 存储 | 每人 ≤ 200 KB，DPAPI 加密 | 与人脸库同级；`runtime/vision/face_registry.bin` 是现成先例 |
| 可删除 | 单人删除即时生效 | 生物特征必须能撤 |

现成可评估的实现（只列候选，不选定）：SpeechBrain / ECAPA-TDNN、3D-Speaker（中文语料更对口）、Resemblyzer。共同点是都能导出 ONNX 走 onnxruntime，与 vision-service 的技术栈一致。

## 五、必须记录的失败模式

1. **短句**：< 1.5 秒不下结论。这是规则，不是调参问题。
2. **远场与设备切换**：本项目已发生过麦克风被切到虚拟设备（"网易虚拟音频设备"）导致听不清的事故；声纹对麦克风变化极敏感，注册与推理必须绑定同一设备链，设备一换就要重估。
3. **相近嗓音**：父子、兄妹之间 EER 会显著变差。必须实测本机家庭成员之间的交叉错误率，而不是只看公开集指标。
4. **跨天漂移**：感冒、疲劳、距离变化会推高 FAR/FRR。需要"置信度带 Time-to-live"而不是一次性注册永久生效。
5. **多人同时说话**：ASR 段里混入第二人声音会污染 embedding，必须检测到多说话人就放弃结论。
6. **误接受的后果分级**（最重要）：见下节。

## 六、动作分级（本设计的核心约束）

声纹结论的可信度不足以驱动所有动作，因此按后果分级：

- **只需称呼**（"你回来了"、"你房间的灯"）：允许使用声纹结论，但不确定时用中性说法。
- **需要指认的动作**（"给我老婆发消息"、"把爸爸房间的空调关掉"）：必须**要求确认**，或者只在置信度高于高阈值时执行；否则回问。
- **安全相关**（跌倒告警推送对象、门锁）：**不允许**只凭声纹执行。

交给模型时，事实必须以"可能"的形式出现并带置信度，例如：

> 声纹判定：可能是爸爸（置信度 0.72），不是确定。

模型据此只能选保守说法。低于阈值时**不注入**该事实，保持与今天一致的诚实回答。

## 七、若获批准的形状（仅供评审，未实现）

- **权威源分离**：位置权威仍归 vision-service（摄像头）；说话人权威归新的声纹模块。两者都带 `source` 字段，谁都不覆盖谁。
- **观测模型**：复用现有契约风格。参考 `contracts.py` 的 `FaceSample` / `FaceQuality` / `RegistrationStatus`，新增 `VoiceSample` / `VoiceQuality` / `SpeakerObservation`，TTL 语义与人脸观测一致。
- **注册入口**：`apps/perception-console` 的「身份」页已有"人脸与未来声纹"的占位，声纹注册应当落在这里，与人脸录入同一个交互范式（分步采样 + 质量反馈 + 成功横幅）。
- **服务归属**：优先并入 voice-service（它已经拥有麦克风与 ASR 段边界），而不是新建第四个服务；只有延迟或依赖冲突时才独立成服务。
- **注入点**：`agent_session.build_system_prompt` 已经负责拼装物理上下文（本轮刚加入 `scene_context`）。声纹结论应作为**同一段上下文的一部分**注入，与人脸/位置并列，不额外增加一轮工具调用。
- **不在链路里做的事**：不做声纹驱动的设备控制，不做说话人绑定房间。

## 八、验收方法（若批准实现）

1. 自建数据集：3 位家庭成员 × 每人不低于 30 句（含远场），另录 2 位"未注册者"用于 FAR 测试。
2. 交叉验证：留出法，报告 EER、FAR、FRR，**按语句长度分档**（<1s / 1–2s / >2s）。
3. 现场验收：注册 3 人，在卧室/客厅各说 10 句，统计称呼正确率与回问率。
4. 回归：确认未识别时仍走今天的诚实路径（不能因为引入了声纹就退化成瞎猜）。

## 九、需要用户拍板的决策点

1. 是否引入声纹？若不引入，本文即归档，"我是谁"保持诚实回答。
2. 注册谁？（全家 / 只注册常用说话人）
3. 是否允许在本机保存声纹生物特征（DPAPI 加密，与脸库同级）？
4. 误接受时允许做什么？（建议：只用于称呼，其余一律确认）
5. 高置信度阈值与低置信度兜底的具体数值（建议先定门槛，再用数据校准）。

## 十、结论

- "我是谁"目前答不出来是**设计使然**，且当前的诚实回答是正确的降级行为。
- 唯一不违反已批准设计的补法是在本机做**声纹**；画面推断方案（C）应继续排除。
- 声纹的工程风险集中在**短语音、远场、相近嗓音**三点，因此建议：**先限制在可逆、指向自己的局部动作**，低置信度不注入。
  细则见 `2026-09-25-speaker-bound-operation-target-design.md`：那里用**后果可逆性**取代了本节早期"只用于称呼、不用于控制"的粗糙说法 —— 声纹可以参与"调我房间的空调"这类操作，但不参与跨主体请求与安全动作。
- 建议先做**离线评估原型**（不进控制链、不进语音主循环），拿到本机真实指标后再决定是否接入。
