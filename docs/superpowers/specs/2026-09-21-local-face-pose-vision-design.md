# 本地人脸识别与人体姿态设计

日期：2026-09-21  
状态：用户已批准功能设计；等待用户审阅本文后编写实施计划。

## 1. 目标

为现有智能家庭项目增加一个完全本机运行的视觉子系统。系统使用同一个手机或电脑摄像头，自动识别已注册的“爸爸、妈妈、孩子”，持续跟踪人物，分析基础人体姿态，并把人物所在房间与视觉状态同步到 Unity。

本阶段不使用通用 VLM。视觉能力限定为：

- 人体检测与连续轨迹；
- 自动人脸身份识别；
- 站立、坐下、躺下、疑似跌倒、举手和未知姿态；
- 单摄像头的逻辑房间选择；
- Unity 内的人脸注册、预览和监控界面。

视觉结果只提供观察信息，不自动控制 Home Assistant 设备，不触发报警，也不声称高安全等级的身份认证。

## 3. 总体架构

新增独立的 `vision-service`，由它独占摄像头和视觉模型：

```text
手机/电脑摄像头
  -> vision-service
       -> YOLO26n-pose：人体框与 17 个骨架关键点
       -> ByteTrack：连续临时轨迹 ID
       -> InsightFace：人脸检测、对齐与身份特征
       -> 姿态状态机：站立/坐下/躺下/疑似跌倒/举手/未知
  -> home-service：有效人物房间、身份、姿态与观察时间
  -> 现有只读 SSE
  -> Unity：小屋人物位置、姓名和姿态状态

Unity <-> vision-service
  -> 摄像头选择、逻辑房间选择、注册命令、状态和本机画面预览
```

`vision-service` 默认只绑定 `127.0.0.1:8766`。`home-service` 继续使用 `127.0.0.1:8765`。Unity 可以向视觉服务发送注册与摄像头配置请求，但仍不发送 Home Assistant 设备控制请求。

## 4. 两种工作模式

### 4.1 注册模式

注册模式使用当前选中的物理摄像头，不关联任何房间。进入注册模式后暂停监控结果发布，避免采集者同时被当作正式位置观察。

流程：

1. 用户在 Unity 选择爸爸、妈妈或孩子。
2. 界面逐步提示正视、向左转、向右转、抬头、低头和眨眼。
3. 每一步只接收单人、单脸、清晰、光线合格、无遮挡且尺寸足够的画面。
4. 系统从不同角度建立多个人脸特征原型，而不是仅保存一张正脸结果。
5. 所有步骤完成后保存特征并立即进入短时识别确认。
6. 用户可取消、删除或重新注册；重新注册以新特征原子替换旧特征。

出现多张脸、动作错误、画面模糊、脸部过小、严重侧遮挡或摄像头中断时，采集暂停并显示具体原因。摇头和眨眼提供基础活体提示，但不承诺抵御照片、录像或深度伪造攻击。

### 4.2 监控模式

监控模式要求用户先选择逻辑房间：`living_room`、`bedroom` 或 `kitchen`。同一个物理摄像头在任一时刻只代表其中一个房间。

- 识别到的已注册人物，其当前有效位置更新为所选房间。
- 未知人物产生轨迹和姿态，但不会绑定到爸爸、妈妈或孩子。
- 切换物理摄像头或逻辑房间时，立即终止全部旧轨迹并撤销旧视觉位置。
- 摄像头关闭、断开或视觉服务停止时，所有由该摄像头提供的位置在宽限期后变为未知。
- 系统不能根据上一次画面推测人物去了其他房间。

## 5. 身份识别与轨迹规则

YOLO/ByteTrack 先产生身体轨迹，InsightFace 的脸框再根据空间包含关系和时间连续性关联到身体轨迹。

人脸识别不必每帧运行。每个活跃轨迹定期复核身份，并使用短时间窗口稳定结果：

- 至少多个有效人脸帧指向同一身份后才确认姓名；
- 最佳候选必须超过配置阈值，并与第二候选保持足够分差；
- 同一个已知身份同一时刻只能绑定一个活跃轨迹；
- 发生冲突时保留证据更强的轨迹，其余显示未知；
- 短暂转头或遮挡可沿用已确认轨迹身份，默认最多 3 秒；
- 轨迹丢失后解除身份，不把后来出现的新轨迹自动当作原人物。

阈值、复核频率、窗口大小和宽限期均放入本地配置。默认值采用保守策略，宁可显示未知，也不能频繁串名。

## 6. 姿态状态机

姿态由连续骨架关键点推导，不能直接由单帧标签决定。

- **站立**：躯干接近竖直，髋、膝、踝关系符合伸展状态。
- **坐下**：躯干仍以竖直为主，但髋膝角与身体高度符合坐姿。
- **躺下**：躯干趋于水平，身体框宽高关系与关键点分布同时支持横向姿态。
- **疑似跌倒**：先观察到明显向下运动或姿态快速变化，再持续进入躺下状态；普通弯腰或直接躺床不能只凭单帧判为跌倒。
- **举手**：至少一侧手腕持续位于对应肩部上方。
- **未知**：关键点不足、遮挡严重、置信度过低或规则互相冲突。

所有状态使用进入与退出滞回，避免在临界姿态之间闪烁。“疑似跌倒”只显示状态，不自动报警、不播放语音、不控制设备。

## 7. 状态模型与 home-service 语义

项目已有 `VisualObservation`、轨迹绑定和丢失语义，但原模型明确禁止从外观推断身份，也禁止摄像头改变人物位置。本设计正式替换这两项旧约束。

扩展后的视觉观察至少包含：

- `camera_id`、`camera_room_id`、`track_id`；
- 归一化人体框和骨架关键点；
- 人体检测置信度；
- `person_id`、人脸相似度、身份确认状态；
- `pose`、姿态置信度；
- `observed_at_ms`、轨迹状态。

`home-service` 保留注册人物目录，但正式运行时不提供手动位置模式。有效人物状态规则为：

- 新鲜且身份已确认的摄像头观察决定人物 `room_id`；
- 快照明确标注 `location_source: "camera"`；
- 观察过期、摄像头失联或轨迹撤销后，`room_id` 变为 `null`、`location_known` 变为 `false`；
- 不回退到历史房间或模拟房间；
- HA 与 Memory 后端都必须合并同一份本地视觉人物状态，避免切换后端时人物消失或恢复旧位置。

视觉服务按批次向 home-service 提交当前活跃观察。home-service 校验摄像头房间、人物 ID、时间戳、坐标范围和重复身份后才提交版本并通过现有 SSE 发布。

## 8. 本地接口

`vision-service` 提供下列 loopback 接口，具体字段在实施计划中固定：

- 查询服务、模型和摄像头状态；
- 枚举并选择物理摄像头或手机视频地址；
- 设置逻辑房间；
- 启动、暂停监控；
- 开始、查询、取消注册；
- 删除指定人物的注册特征；
- 获取最新压缩预览帧和实时视觉结果。

`home-service` 新增仅供本机视觉服务提交观察、撤销轨迹和报告摄像头离线的受限接口。该接口不能调用设备工具，也不能修改灯、空调、插座或温度传感器。

## 9. Unity 界面

Unity 现有小屋与 HA 状态界面保持不变，新增独立摄像头面板：

- 物理摄像头来源选择；
- 逻辑房间选择；
- 注册爸爸、妈妈、孩子；
- 注册动作、进度、质量提示、取消、删除和重新注册；
- 当前画面、人体框、骨架、姓名、姿态和置信度；
- 服务状态、模型加载状态、摄像头断线、无人、未知人物和人脸过小提示。

画面叠加使用归一化坐标，适配不同摄像头分辨率。视觉处理来不及时丢弃旧帧，只处理最新帧，禁止形成不断增长的延迟队列。

## 10. 本地数据与隐私

- 摄像头原始帧只存在于内存和 Unity 当前预览，不默认写入磁盘。
- 人脸特征存放在 Git 忽略的 `runtime/vision` 下，并绑定当前 Windows 用户进行本地加密。
- 删除注册人物时同时删除该人物的全部特征原型。
- 日志不能记录原始图像、人脸特征、完整视频地址或可恢复生物特征的数据。
- 接口只绑定 loopback，不向局域网公开。

## 11. 故障与诚实状态

- 摄像头打开失败：显示具体错误，人物位置保持未知。
- 模型未加载或推理异常：撤销正在发布的视觉状态，不能继续显示旧结果。
- 多脸注册：暂停并要求画面只保留注册者。
- 无脸、脸太小或质量不足：保持轨迹但不确认身份。
- 物理摄像头或房间切换：先清空旧状态，再启动新会话。
- `vision-service` 与 home-service 断开：本地可继续预览，但人物位置不能声称已同步。
- Unity 与视觉服务断开：小屋通过 home-service 的过期规则回到位置未知。

## 12. 性能边界

- 摄像头采集、人体姿态、人脸识别、状态上传和 Unity 预览使用有界队列。
- 队列只保留最新帧，旧帧可以丢弃。
- YOLO Pose 优先使用 RTX 4060；人脸复核可降低频率并按实际负载选择 GPU 或 CPU。
- 同一时刻只初始化一个物理摄像头流。
- 模型加载和摄像头重连不得阻塞 Unity 主线程。

本阶段不承诺固定 FPS 或识别率数字；这些数值由用户手动测试后记录。

## 13. 用户手动验收约束

用户明确要求实现者不进行任何形式的测试。实现过程中及完成后不得运行：

- 单元、集成或端到端测试；
- Unity 编译、批处理、PlayMode 或 EditMode 检查；
- Python 模型推理、摄像头采集或注册试跑；
- 截图、视频或视觉效果验收；
- 以测试为目的的服务启动或真实状态读取。

实现者只能完成代码、配置、模型接线和界面，并及时报告依赖缺失、接口冲突、无法继续或需要用户选择的问题。交付措辞必须为“已实现，尚未验证”，不能声称功能可用、测试通过或识别准确。

用户手动检查的主功能包括：

1. 三名家庭成员分别完成注册。
2. 已注册人物自动识别，未注册人物显示未知。
3. 多人、转头、短暂遮挡时不频繁串名。
4. 站立、坐下、躺下、疑似跌倒和举手状态可观察。
5. 客厅、卧室、厨房切换后人物位置来源正确。
6. 摄像头切换、断线和人物离开后不保留陈旧位置。
7. Unity、视觉服务、home-service 和现有语音服务可以同时启动。

## 14. 后续声纹识别与视听融合

用户明确要求后续增加声纹识别，并与视觉身份结合。本阶段不实现声纹，但预留以下边界：

- 人脸身份结果必须携带时间范围、轨迹 ID、置信度和来源摄像头；
- 未来声纹服务输出独立的 `speaker_observation`，包含候选人物、置信度、音频时间范围和来源麦克风；
- 融合层只在时间窗口、房间来源和置信度共同满足条件时增强身份判断；
- 人脸与声纹冲突时不得强行选择，必须输出身份不确定；
- 视觉中出现某人不代表该人正在说话；声纹识别也不能直接推断其画面轨迹；
- 人脸特征与声纹特征分开注册、保存和删除，不能互相替代。

## 15. 明确不做

- 通用场景问答和 VLM；
- 多摄像头同时运行、跨摄像头 ReID 和轨迹交接；
- 人脸认证、门禁或支付；
- 自动设备控制、自动报警或救援决策；
- 保存连续录像；
- 本阶段的声纹识别和视听身份融合；
- 手动人物位置模式。
