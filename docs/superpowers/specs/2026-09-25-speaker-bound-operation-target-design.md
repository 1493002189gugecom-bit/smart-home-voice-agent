## 一、要修正的结论

上一份评估把动作分成"称呼"与"控制"两类，并禁止声纹参与后者。这是错的，因为它用**动作种类**而不是**后果**来分级。

用户的实际诉求是合理的：「帮我把空调调低 2 度」应当理解为"调低**我所在房间**的空调"。这需要三件事串起来：

1. 声纹 → 说话人是谁（`dad`）
2. 摄像头 → 这个人在哪个房间（`bedroom`）
3. 房间 → 该房间的空调设备（`bedroom_ac`）

第 1 步只有声纹能做，所以声纹确实是操作链的一部分，不是可有可无的装饰。

正确的分级是**后果可逆性**，见第三节。

## 二、先说两个坑（这是本设计的全部难点）

### 坑 1：位置不是随时都有的

位置只来自摄像头，且带 TTL（`observation_ttl_ms = 3500`）。人刚走进卧室、还没被识别到人脸时，`location_known = false`。

所以「我在哪」在物理上**经常答不出来**，这不是 bug。此时"按你的位置操作"必须**停止并追问**，绝不能退回"上一次已知的房间"或猜一个。

### 坑 2：这是两路推断串联，错一个就错到底

`声纹正确` × `位置新鲜` 才是可靠目标。两路的失败会叠加：

| 声纹 | 位置 | 结果 |
| --- | --- | --- |
| 对 | 新鲜 | ✅ 正确房间 |
| 错（FAR） | 新鲜 | ❌ **静默调错房间**（最危险：用户以为调的是自己房间） |
| 对 | 未知 | ⚠️ 必须追问，不能猜 |
| 错 | 未知 | ⚠️ 追问即可，无害 |

第二行是本设计必须处理的唯一真风险。它不像"称呼错了"那样立刻能察觉 —— 用户可能过很久才发现客厅空调被调了。

## 三、后果分级（替代原来的"称呼 vs 控制"）

| 动作 | 声纹可用？ | 理由 |
| --- | --- | --- |
| **指向自己、可逆、局部**：我的灯/我的空调/我房间的插座 | ✅ 可用，但**必须播报房间名** | 最坏情况是调错房间，一句话改回来 |
| **显式房间**：「客厅空调调低」 | ✅ 无关，直接用显式房间 | 声纹不参与，零新增风险 |
| **跨主体**：「给爸爸房间关空调」「给妈妈发消息」 | ❌ 必须显式说清或追问确认 | 意图涉及第三方，误判影响他人 |
| **不可逆 / 越界 / 安全**：门锁、告警推送对象、全屋场景、批量操作 | ❌ 禁止 | 误判后果不可用一句「不是」挽回 |

关键区别：**允许声纹影响的只有"省略房间时默认指自己"这一个语义**，不允许它去改变用户已经明说的目标。

## 四、核心机制：`self` 符号 + 本地解析

不要让模型自己完成"声纹→位置→设备"的推断。模型的散文不可测试、不可审计，而现有架构的原则是**写操作的目标以服务确认为准**。

做法：

1. 工具参数新增一个**枚举值**：`target`，取值 `"self"` 或省略（沿用现有 `device_id`）。
2. 模型在用户省略房间时输出 `target: "self"`，**它不负责解析**。
3. 由一个**本地确定性解析器**把 `self` 变成 `device_id`：

```
resolve_self_target(kind, speaker_id, now_ms)
  ├─ speaker_id 为空（声纹不可用/未注册/低置信度）
  │     → 追问："你是想调哪个房间的空调？"
  ├─ speaker_id 有，但该人 location_known = false
  │     → 追问："我现在没看到你在哪个房间，你要调哪个房间的？"
  └─ speaker_id 有，且 location_known = true
        → room_id = 该人的 room_id
        → device_id = 该房间内 kind 类型的设备（唯一）
        → 若该房间没有此类设备 / 有多台 → 追问，不猜
```

这个解析器是纯函数，输入 `(kind, speaker_id, 位置快照)`，输出 `device_id | 追问原因`，可以像 `normalize_arguments` 一样写满单元测试。这是本设计最重要的一条：**"谁算我"由本地代码决定，不由模型决定。**

复用现有结构：`agent_tools.normalize_arguments` 的 `_ALLOWED_ARGUMENTS` / `_require_choice` 加分支；home-service 已经能按房间列出设备，无需新路由。

## 五、把静默错误变成可纠正错误

针对坑 2 第二行（声纹认错 + 位置新鲜），不新增阻塞式确认（会让每次操作都多一轮，体验崩坏），只加一条**播报约束**：

> 任何由 `self` 解析出的写操作，播报**必须包含解析出的房间名**。

- ❌「好的，已经调低了。」
- ✅「好，**卧室**空调调低 2 度。」

这条约束的成本极低（改 system prompt 与播报文案），但把 FAR 的后果从"静默错误"降级为"用户一听就能纠正"。用户听到"卧室"不对，立刻说「不是，是厨房」即可。

注意与现有机制的区别：`OperationStore` 的 `confirmation_timeout` 是**设备状态确认**（HA 回报），不是用户口头确认。本设计**不**要求用户二次口头确认。

## 六、契约与数据改动（最小集）

1. **声纹结果必须复用 `persons.json` 的同一个 id 空间。**
   声纹库不能自建 id，否则"声纹的爸爸"和"人脸的爸爸"会是两个人，第 1、2 步就对不上。注册声纹时必须绑定既有 `person_id`。
2. **新增声纹观测契约**，风格对齐 `contracts.py` 的 `FaceSample` / `FaceQuality` / `RegistrationStatus`：
   - `SpeakerSample`（embedding 质量、时长、SNR 指标）
   - `SpeakerObservation`（`person_id`、`confidence`、`observed_at_ms`、TTL）
   - 与人脸观测同构，便于两路证据将来并列注入。
3. **注入方式**：与 `scene_context` 并列写进 system prompt，例如
   `声纹判定：可能是爸爸（0.72）。`
   低于阈值则**不注入**，模型行为退化为今天的样子（追问）。
4. **不改**：位置权威仍属 vision-service；声纹不产出房间。

## 七、两阶段落地（建议）

### 阶段 A —— 只读版（先做，风险≈0）

声纹结果只进 prompt，写操作仍要求显式房间。

- 收益：对话自然（"你卧室的空调现在 26 度"）、跨轮记忆、"我是谁"能诚实且有用。
- 风险：无。没有 `self` 解析，就没有坑 2。
- 顺带把声纹门槛、注册流程、FAR 实测跑完 —— 这些是阶段 B 的前提。

### 阶段 B —— 放开"自己房间"的写操作

- 前提：阶段 A 的现场实测 FAR 达标（建议 ≤ 1%，且**语句 ≥ 1.5 秒**才下结论）。
- 内容：启用 `target: "self"` 与 `resolve_self_target`，加播报房间名约束。
- 回滚开关：一个配置项即可关掉 `self` 解析，退回阶段 A。

## 八、验收指标

| 指标 | 门槛 |
| --- | --- |
| 声纹 EER / FAR | 沿用评估文档（≤ 5% / ≤ 1%，仅 ≥1.5 秒语音） |
| **目标房间正确率** | ≥ 99%（"我房间的空调"解析到正确设备） |
| **未知位置时的追问率** | 100%（不允许猜） |
| 误解析后果 | 必须能被一句播报察觉（播报含房间名） |
| 跨主体请求 | 0 例被 `self` 静默替代 |
