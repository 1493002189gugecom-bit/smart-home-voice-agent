# 感知中心界面、可见人脸注册与音频设备选择设计

日期：2026-09-24
状态：方案已在对话中确认；待用户审阅本规格后编写实施计划

## 1. 目标与边界

感知中心应让家庭成员一眼看清摄像头、语音、人物和设备的真实状态。人脸注册必须能看见自己正在被哪台摄像头拍摄，并能据此修正取景；语音应优先跟随 Windows 系统默认输入和输出设备，失败时给出可理解、可选择的备选设备。Unity 仍只做 home-service 状态展示，不增加视觉或语音控制。

沿用 `perception-console :8770 → vision-service :8766 / voice-service :8767 / home-service :8765` 的同源代理结构。不新增远程访问、云端媒体存储或声纹模型。原始视频和音频不落盘；页面对话记录仍仅保留当前会话。

## 2. 已确认的现状与问题

- 身份页只有人物卡片和注册进度，没有任何 MJPEG 画面；视觉页的实时预览未复用到注册流程。这解释了点击注册后无法看见自己。
- 当前 vision-service 正在使用 `device:0`，另可枚举 `device:2`；模型状态为 ready，`preview.jpg` 返回 200。历史注册会话已取消，因此仅凭当前状态不能判定先前的 `no_face` 是错误摄像头、取景、光线还是推理缺陷。
- voice-service 当前未监听 8767。旧的默认参数把输入、输出都固定为 HyperX；系统音频端点中 HyperX 状态异常、Realtek 正常。语音控制 API 在设备和模型初始化之后才绑定，故初始化失败只能表现为 `down · URLError`。
- 语音页当前只显示可枚举设备名称，没有“系统默认”“正在使用”“可选择”或设置生效提示。
- 当前界面通篇深绿小卡片，`body` 最小宽度为 1080px，在较窄应用窗口会横向溢出。

## 3. 界面方向

采用安静、温暖、清晰的本地工作台风格：浅暖灰背景、奶白内容面、深墨色文字、低饱和青绿色主动作、琥珀色等待提示、朱红色故障提示。避免同等权重的卡片堆叠；将正在发生的画面和当前关键状态作为视觉中心。统一 8px 间距节奏、清晰的标题/正文/辅助文字层级、可见的焦点环和至少 44px 的操作目标。图标使用同一套 SVG 线性风格，不以 emoji 表示功能。

桌面宽屏保留侧栏；中等宽度改为紧凑导航；窄窗口改为顶部或底部可见导航，不设固定 1080px 最小宽度。信息内容在 375px 宽度仍能阅读、操作和滚动，不产生页面级水平滚动。动画只用于状态过渡，遵守减少动态效果设置。离线、连接中、已过期和真实在线状态必须同时用文字表达，不只依赖颜色。

总览优先显示当前运行概况、最近人物位置和对话；视觉页以大幅实时画面为主；语音页区分当前状态、会话时间线和设备设置；身份页以注册引导为主，人物卡片退居选择入口；服务页展示可恢复原因，不把原始异常类型当成唯一提示。

## 4. 人脸注册流程

点击某人的“注册 / 重新录入”后，身份页进入专用注册工作区，不跳转到没有画面的状态卡。工作区始终包含：当前人物、当前摄像头、实时 MJPEG 画面、明确的画面状态、六步进度、当前动作和本步合格样本数量，以及取消入口。画面断开立刻隐藏，显示重试或换摄像头操作，不展示旧帧为实时画面。

若尚未选摄像头，先列出可枚举设备让用户选择，未选择前不调用注册 API。已选摄像头时可直接启动注册并在同一工作区显示画面；如果第一帧迟迟未到，显示“正在等待摄像头画面”，而不是立即提示用户面对摄像头。注册期间切换摄像头需先明确取消当前会话，再选择设备并重新开始，避免后台将旧样本归入新摄像头会话。注册完成或取消后保留明确结果及返回入口。

前端把后端 `quality_reason` 映射为用户可执行的中文指导，尤其区分：未检测到人脸、多人入镜、距离/角度/光线不合格、动作不匹配、模型或摄像头异常。未知错误保留安全的通用文案和错误代码，避免把 `no_face`、`URLError` 等内部字串直接作为主要说明。对于“没有人脸”，界面同时展示实时画面和当前摄像头，让用户能判断镜头是否拍到了自己。

不放松原有的六步注册质量阈值，也不把“画面里有人”误报为“合格样本”。若实机画面确实有人脸、模型健康、单人正面且连续多帧仍稳定返回 `no_face`，再针对视觉流水线做独立缺陷修复和回归测试；不靠改提示文案掩盖识别缺陷。

## 5. 语音设备策略与接口

默认自动模式先读取 PortAudio/Windows 的系统默认输入和输出端点，并分别验证其所需采样率、声道和格式；有效则采用。若默认端点不可用，按可枚举且实际可打开的候选设备回退，不再把 HyperX 作为强制默认参数。用户手动选定的设备优先于自动策略；保存稳定的设备名称与 host API 匹配信息，不持久化易变化的设备索引。被选设备消失时回退到自动策略并明确提示，不静默选到错误的虚拟设备。

`GET /devices` 返回输入与输出的安全摘要，以及每项的系统默认、当前使用、可用状态；不返回硬件标识或敏感路径。`POST /devices/select` 分别接受输入与输出的“自动”或设备匹配信息，验证后保存偏好，并由 voice-service 重新创建音频流；失败时保留原可用流或进入明确的 degraded 状态。语音页分别提供“跟随系统默认”和已验证可用设备的选择控件，显示应用中与最终成功/失败状态，不把待应用选择伪装为已生效。

Voice API 应在耗时设备/模型初始化前绑定 loopback。初始化失败时进程保留可查询的 `degraded` 状态、受限的错误代码和设备列表，而不是直接消失；不得把密钥、模型路径、原始音频或转写写入错误响应。设备重选后由同一进程重试初始化；服务真正退出时控制台仍应显示“服务未运行”而非仅显示网络异常类名。

## 6. 数据与安全

React 只请求 8770。新语音设置操作经 8770 的明确路径白名单代理到 8767，禁止任意 URL 转发。所有控制端点仍只绑定 `127.0.0.1`，请求体限流和内容类型校验沿用现有网关规则。设备偏好仅保存在 git-ignored 的本地运行配置中，不包含录音、画面、转写或密钥。注册预览只以现有 MJPEG 流传输，不新增帧持久化。

## 7. 验证与验收

用户已在 2026-09-24 明确允许本次运行模型推理及针对性测试，以查明“没有人脸”是否为 bug。先做单元/接口回归，再构建 React；随后在用户当前连接的摄像头上执行短时、受控的人脸注册观察，检查画面、摄像头标识、质量提示和进度是否一致。不得将实机画面、音频、转写或人脸特征输出到测试日志或截图文件。若测试需要真实录入某位家庭成员的持久化特征，应先取得该成员的明确选择；默认只观察检测与进度，并取消会话，不覆盖已有注册数据。

音频验证覆盖系统默认可用、默认不可用后回退、手动选择、设备消失与初始化失败状态。运行时如需打开麦克风或扬声器，只做短时设备可用性验证，不录音落盘、不主动播报私人内容。UI 验证覆盖桌面与窄窗口、键盘焦点、断线/重连及降低动态效果。

完成标准：注册时可持续看到同一摄像头的实时画面；画面里有人脸而检测始终返回 `no_face` 时有可复现证据和修复，不以猜测结案；语音能默认使用系统设备或明确回退，且设备选择与实际生效状态一致；控制台在任一服务故障时仍可用并给出可恢复提示。
