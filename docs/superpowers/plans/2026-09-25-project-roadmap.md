## 7.1 当前架构、已具备能力和边界

- 主仓库为 `E:\smart-home`：本地语音服务（唤醒、VAD、SenseVoice ASR）、视觉服务（姿态、轨迹、人脸）、`home-service`、Home Assistant/MQTT、React/TypeScript/Vite 感知终端。DeepSeek 负责受限工具决策，Edge TTS 负责在线语音合成。
- 实际 Unity 工程在独立目录 `E:\unityroom\unityroom`，Unity 2022.3、Built-in Render Pipeline、uGUI；Blender 场景和只读插件也由此项目维护。Unity/Blender 通过 `home-service` 的 SSE/快照展示家庭状态，不是设备控制或人物位置的权威来源。
- `home-service` 应继续作为设备状态与操作结果的权威层；人物运行时房间只由摄像头可信观察决定，未知、过期或失联时显示未知。人物目录可增加自定义身份，但房间、设备和部分 UI/场景布局仍固定为三房间、八设备。
- 既有 HA 闭环、人物房间移动和 Unity SSE 曾有验收记录；当前主仓库还有大量未提交改动，Unity 是独立非 Git 工程。后续每项完成状态必须用针对**当时版本**的新证据更新，不能沿用旧报告。

## 7.2 产品质量原则

1. **结果要有来源与时效。** 明确区分进程在线、模型就绪、摄像头出帧、最近一次可靠人物观察、HA 同步和设备操作确认。终端与 Unity 使用相同含义的状态。
2. **说了才控制。** 用户提出设备意图时可结合可信说话人和最近房间观察选择设备；身份不明、位置过期或候选设备不唯一时，给出有针对性的澄清。传感器观察本身不触发设备操作。
3. **回复以操作记录为准。** `confirmed`、`unconfirmed`、`rejected` 和部分成功必须分别播报；模型生成的自然语言不得覆盖执行结果，也不得让超时后的用户误以为可以无风险重复调节。
4. **房间级定位先于精确站位。** 未做摄像头到房间平面的标定时，只承诺“人在客厅/卧室/厨房”，不把画面像素换算出的 3D 坐标当作真实站位。
5. **先测瓶颈，再换模型。** 分开统计采集、检测、人脸、ASR、决策、设备确认、TTS 首音和 Unity 展示延迟；依据真实数据决定是否更换模型或计算后端。

### 房间内站位的前提与实验路径（2026-09-26 补充，尚未实施）

用户反馈：现有电脑摄像头难以持续看见脚部落点，也不能看见整个房间。当前 `home-service` 的人物 `x/y` 是画面归一化坐标（人物框中心与底边），Unity 将其换算为房间偏移会造成“已知道真实站位”的错觉；这些值没有空间标定依据。

1. **先完成 P0-5 的诚实房间级显示。** 摄像头只提供可信人物身份、绑定房间、观察时间和是否仍可见。Unity 在该房间的固定展示锚点显示人物与来源/时间，不根据画面 `x/y` 移动人物；切换摄像头的房间绑定、跟踪丢失、观察过期或断线时撤销旧位置。这个阶段不需要完整 3D 房屋模型，也不依赖脚部可见。
2. **将精确站位作为 P2 可行性实验，而非当前功能承诺。** 先确认是否存在固定、稳定、覆盖目标活动区域且能持续看到地面的机位；桌面摄像头若主要只拍到脸和上半身，就不进入地面定位开发。试验时只需简化的房间地面轮廓及少量可复核的地面对应点，不要求家具和墙面与现实完全一致。记录脚部/身体与地面接触点的可见率、遮挡、镜头移动、标定误差和丢失恢复情况；脚部不可见时不得把人物框底边或头部位置当作真实落地点。
3. **只有实验通过才实施坐标映射。** 固定机位下，在画面与简化地面图中配对至少四个不共线、确实位于地面的点，校正镜头畸变后计算地面平面映射；把可信落地点投到 Unity 地面坐标，并显示误差/置信度。低置信度、遮挡、越出视野、机位变动时退回房间级或未知。若单机位有不可接受的盲区，再评估另一固定摄像头或深度设备；多机位也不能看穿所有遮挡。

验收边界：P0-5 以**房间正确、来源与时间真实、过期回落**为准；P2 的站位实验需在实际机位上验证，未取得可复核的误差与覆盖数据前，不把人物模型的房间内移动标为“真实位置”。

## 7.4 技术栈与界面决策

- **保留当前服务栈，先消除实际瓶颈。** Python 服务、React/TypeScript/Vite、Home Assistant 与 Unity 的职责划分适合当前目标。不要只因识别慢就替换语义模型或视觉模型；优先完成 P0-6 的时延剖析和真实错误分类。频繁且明确的设备指令可走受限确定性路径，复杂表达才交给云端决策。
- **视觉按设备调校。** 摄像头请求 1280×720/30 FPS 不等于实际输出达到该模式；终端应显示实际模式。固定清晰度/亮度阈值需要按不同摄像头、光照和距离统计误拒率，而不是无依据放宽门槛。手机流可以作为后续输入方式，但需要明确配对、权限、断线和隐私流程。
- **网页信息层级。** 顶部优先放“能否对话、能否识别、设备是否真实可控”的摘要，再展示服务细节；不同状态用中文词、图标和更新时间共同表达，不只靠红绿颜色。保留现有简洁浅色视觉语言，减少密集状态卡与弹窗，把注册完成和错误提示留在当前工作区。
- **Unity 视觉方向。** 先修空间比例、家具语义、灯具位置与标签遮挡，再提升模型和材质细节。当前 Unity 2022.3/Built-in RP 可继续使用；若评估 Unity 6 LTS 或 URP，先在隔离副本验证插件、材质、场景和测试，再决定迁移，不把管线升级当作当前闪烁问题的替代修复。
- **安全、隐私与文档。** 准确列出发给 DeepSeek 的转写及人物/房间/设备上下文和发给 Edge TTS 的回复文本；提供最小化选项。对外分发前核对视觉模型、唤醒资源、素材的使用许可。README 的能力状态要与当前验证记录一致。

## 7.5 建议实施批次

1. **可靠性基线：** P0-1、P0-2、P0-6。先让失败可定位、成功可确认，并取得实际延迟与识别质量数据。
2. **可信决策与展示：** P0-3、P0-4、P0-5。用同一批人物移动、短句、断线和设备操作场景验证网页、语音与 Unity 的一致性。
3. **可维护性与扩展：** P1-1 至 P1-4。统一配置、接口边界、前端事件流和 Unity 工程来源。
4. **新增能力：** P2。依据前面验收数据决定多摄像头、手机接入、精确定位和更丰富的数字孪生表现。

每批开始时记录基线和目标；完成后把真实命令、版本、结果及未通过项写入新的 `docs/superpowers/reports/` 报告。摄像头/人脸主功能继续由用户手动验收，不在后台擅自启动设备或声称识别率已达标。
